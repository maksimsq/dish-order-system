# Курсова робота: Вебзастосунок замовлення страв (Варіант 11)

Програмна система призначена для автоматизації процесів вибору страв, конфігурації замовлень з модифікаторами, бронювання часових інтервалів отримання та оперативного керування кухнею закладу громадського харчування.

---

## 1. Ролі користувачів та сутності
- **Відвідувач (клієнт)**:
  - Перегляд структурованого меню з категоріями, фотографіями, детальним описом.
  - Ознайомлення зі складом кожної страви та навчальною інформацією про алергени (без медичних рекомендацій).
  - Конфігурація порції за допомогою груп модифікаторів (обов-язковий вибір розміру, додаткові топінги, соуси з контролем мін/макс кількості).
  - Кошик із вибором способу отримання (самовивіз / у закладі) та фіксацією часового інтервалу.
  - Відстеження статусу замовлення в реальному часі через Server-Sent Events (SSE) з автоматичною повторною синхронізацією при розриві інтернет-з-єднання.
- **Оператор закладу**:
  - Захищена панель керування замовленнями (потрібен токен доступу).
  - Зміна статусів замовлень: «нове» -> «готується» -> «готове» -> «виконано» (або «скасовано»).
  - Керування доступністю страв ("стоп-лист" кухні).
  - Керування робочим станом закладу (перемикач «відчинено / зачинено») та лімітом пропускної здатності часових інтервалів.

---

## 2. Реалізація обов-язкових вимог та граничних випадків (Варіант 11)
1. **Серверний розрахунок загальної суми**:
   - Розрахунок цін проводиться виключно на бекенді на основі діючих тарифів у базі даних SQLite.
2. **Закритий заклад**:
   - Якщо оператор перевів заклад у статус «зачинено», нові замовлення автоматично блокуються на сервері з відповідним повідомленням.
3. **Зміна доступності страви**:
   - Якщо страву вимкнено в панелі оператора, сервер повертає помилку при спробі створити з нею замовлення.
4. **Дублювання підтвердження (ідемпотентність)**:
   - Клієнт генерує унікальний `idempotencyKey`. Повторне надсилання форми не створює дублікатів замовлення та не списує квоту слота.
5. **Спроба клієнта встановити статус «виконано»**:
   - Маршрути зміни статусів захищені перевіркою ролі оператора. Будь-яка клієнтська спроба повертає HTTP 403 Forbidden.
6. **Обмеження пропускної здатності часових інтервалів**:
   - На кожен інтервал (наприклад, 20 хв) встановлюється максимальна кількість замовлень. При вичерпанні ліміту слот стає недоступним.
7. **Події оновлення статусу (SSE) та відновлення після розриву зв-язку**:
   - Використовується Server-Sent Events. Клієнтський інтерфейс відображає індикатор стану мережі та автоматично відновлює актуальні дані через повторний запит.

---

## 3. Технологічний стек
- **Бекенд**: Node.js, Express, вбудована бібліотека `node:sqlite` (SQLite3).
- **Фронтенд**: React, Vite, CSS3 (адаптивний дизайн для ПК та мобільних пристроїв), Lucide іконки.
- **Протокол оновлень у реальному часі**: Server-Sent Events (SSE).

## 4. Швидкий запуск

### Варіант А. Запуск усього проєкту однією командою (через сервер):
```bash
node server/src/server.js
```
Після цього відкрийте у браузері: **http://localhost:5000**

### Варіант Б. Запуск у режимі розробки (окремо бекенд та фронтенд з гарячим перезавантаженням HMR):
1. **Бекенд**:
   ```bash
   node server/src/server.js
   ```
2. **Фронтенд**:
   ```bash
   cd client
   npm run dev
   ```
   Фронтенд буде доступний за адресою: **http://localhost:3000**

## 5. Сценарій навантажувального тестування (Load Testing)

Для верифікації та точного повторення замірів продуктивності (RPS, латентність p50/p95/p99), наведених у розділі 5 пояснювальної записки, у реліз додано автоматизований навантажувальний тестовий комплекс (`scripts/load-test.js`).

### Як запустити навантажувальний тест:
1. Переконайтеся, що бекенд-сервер запущено:
   ```bash
   node server/src/server.js
   ```
2. В окремому терміналі виконайте команду запуску навантажувального тесту:
   ```bash
   npm run test:load
   ```
   *(або напряму: `node scripts/load-test.js`)*

### Що перевіряє сценарій:
- **Сценарій 1 (Читання каталогу `GET /api/menu`)**: 500 запитів при 50 одночасних з-єднаннях (RPS ~800, p95 < 70 мс).
- **Сценарій 2 (Запит часових інтервалів `GET /api/slots`)**: 500 запитів при 50 одночасних з-єднаннях (RPS ~700, p95 < 85 мс).
- **Сценарій 3 (Створення замовлень `POST /api/orders`)**: 60 транзакцій із серверним підрахунком вартості за тарифами бази SQLite при 10 паралельних потоках (RPS > 450, p95 < 90 мс).
- **Сценарій 4 (Стрес-тест ідемпотентності)**: 50 одночасних повторних кліків з однаковим ключем для доведення 100% захисту від дублювання та блокування подвійного списання квот.

### Очікувані еталонні показники:

## 6. Інтерактивні функціональні перевірки (Лабораторний модуль)

Для демонстрації викладачу виконання всіх обов-язкових вимог Варіанта 11 у вебінтерфейсі реалізовано модальне вікно перевірок (іконка колби у верхньому меню `http://localhost:5000`):
1. **Закритий заклад**: перевірка блокування замовлень, коли заклад зачинено (HTTP 400).
2. **Недоступна страва**: блокування позицій зі стоп-листа кухні (HTTP 400).
3. **Подвійний клік (ідемпотентність)**: надсилання двох однакових запитів з одним ключем (єдиний номер замовлення у базі).
4. **Зміна статусу клієнтом**: перевірка захисту ролей та коду HTTP 403 Forbidden.
5. **Ліміт слотів**: перевірка блокування замовлення при вичерпанні ліміту пропускної здатності часового інтервалу (HTTP 400).
6. **Живий SSE-трекінг**: перевірка отримання технологічних статусів у реальному часі через Server-Sent Events.
